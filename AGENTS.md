# Roam

Expo React Native rental app. Guests describe a stay in one sentence ("quiet pet friendly cabin with a hot tub under $300 a night") and get ranked stays back. They can also ask booking and policy questions about a stay, answered with exact text from Roam's own content.

This file is the project's memory: it holds every decision that is still true. Plans in `prompts/` are history.

## Commands

```bash
npx expo install <package>  # ALWAYS use instead of npm install: resolves SDK-compatible versions
npx expo start              # dev server (press i for the iOS simulator)
npx expo lint               # lint
npx tsc --noEmit            # type check
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
npx eas-cli@latest <cmd>    # EAS builds, submits, and updates (use instead of bare `eas`)

# In studio/ (its own package; root tsc and lint skip it, and `npm install` is fine there)
npx sanity schema validate                         # check schema
npx sanity@latest schema deploy                    # deploy schema
npx sanity@latest deploy                           # deploy hosted Studio (https://rn-roam.sanity.studio)
npx sanity exec seed/seed.ts --with-user-token     # seed (re-runnable, uses your CLI login)
npx sanity exec copy/write-copy.ts --with-user-token [-- --check]  # write stay copy (or only audit it)
npx tsx copy/grounding.check.ts                    # self-check of the code invention check
```

## Expo

- Expo ships breaking changes every SDK release, so don't trust memory. Before touching an Expo, EAS, or React Native API, check the `expo` major version in `package.json` and read `https://docs.expo.dev/versions/v<major>.0.0/`. For anything else, start from https://docs.expo.dev/llms.txt and follow its links.
- Routes live in `src/app/`: every file is a screen and `_layout.tsx` files define navigators. API routes are `src/app/api/*+api.ts`. Keep components, hooks, and utils outside `src/app/`.
- Screens: `index` is onboarding (every signed-out launch). `sign-up` → `verify` → `home`, and `sign-in` → `home` (via `verify?flow=sign-in` when Clerk asks for a new-device code). The root layout guards routes with `Stack.Protected` on Clerk's `useAuth()`: the `(tabs)` group is signed-in only, onboarding and auth screens are signed-out only, and the guard flip does the navigation after sign-in and sign-out (never `router.replace` into `home`). The splash stays up until fonts and Clerk are loaded. Root `Stack` hides headers; a screen that wants one sets `headerShown: true`.
- Signed-in screens live in `src/app/(tabs)/` under `NativeTabs` (`expo-router/unstable-native-tabs`): Home, Search, Trips, Profile, in that order (URLs `/home`, `/search`, …). Search is a plain tab, not `role="search"`. Home's field opens `/search?q=`, and a new `q` replaces Search's text and runs it. Search has a back button (to Home), the four chips (Cabins, Under $300, Pet Friendly, Quiet), a native sort menu (`sort-menu.ios.tsx` SwiftUI `Menu`, `sort-menu.tsx` Compose `DropdownMenu`, both with an RN label through `RNHostView`), and a filter sheet (RN `Modal` pageSheet, edits apply on "Show stays"). Chips and the sheet edit the parsed filters, never the text; submitting text re-parses and drops them. Trips lists confirmed bookings (Upcoming, then Past; rows push the stay with `from=trips`; a muted line until there are any), then saved stays under "Saved" (newest first, `from=saved`). Hearts on Search, the stay screen and Trips share `useSaved()` (`src/lib/saved.ts`). Profile follows the design: wordmark and gear (pushes `account/settings`), photo/name/home-city card, Account and Preferences `ListGroup`s (Personal info pushes `account/personal-info`; Payment methods and Notifications say "Coming soon"; Trips opens the tab; Help mails `SUPPORT_EMAIL` from `src/lib/ask.ts`), and a cancellation banner whose sheet lists Roam's cancellation policies word for word. The design's stats card and badge stay hidden until there's data. `account/settings` (Devices with sign-out of other sessions, Sign out, Delete account) and `account/personal-info` (photo, first/last name, home city; email read-only) are root Stack screens in the signed-in group with headers. Profile shows a Hosting group only to host company members (Hosting row) and invitees ("Join <company>" rows that accept and open Hosting). `host/index` (makes the company active, picker when several, Team and Switch company rows, the company's stays), `host/stay/[id]` (edit form for the typed fields) and `host/team` (members, pending invitations; admins invite, change roles, remove and revoke, but never act on themselves, so a company keeps an admin) are root Stack screens in the signed-in group with headers. No design exists for them; they use existing components only. `stay/[id]/index` is a root Stack screen in the signed-in group, pushed from Home's `StayCard` and Search's `ListingCard` with `from=home|search`: photo pager, features (top 3 amenity badges plus the setting), an Ask about policies row that pushes `stay/[id]/ask`, cancellation and host rows that open `InfoSheet` page sheets, room counts and description, and a footer whose Book button pushes `stay/[id]/book`: check-in/out `DateField`s (`date-field.ios.tsx` SwiftUI `DatePicker`, `date-field.tsx` Compose `DatePickerDialog`), a guest `Stepper`, the price, the cancellation policy row, then Stripe's PaymentSheet, then "Confirming…" until the server reports `confirmed` (polls 30 s, then "Payment received"). `stay/[id]/ask` is a chat: topic chips (Cancellation, Check-in, Pets, House rules) send a question, the input has a message icon, and each reply is one `AnswerCard` per topic (source label, text word for word) or the support line; it opens with one sample exchange and isn't persisted. A tab screen's first child is its `ScrollView` with `contentInsetAdjustmentBehavior="automatic"` (iOS insets it); Android adds the top inset by hand.
- `ios/` and `android/` are generated. Never create or edit them by hand; configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, switch to a development build (`npx expo run:ios`).

## Who owns what

Each tool has one job. Ask before moving a responsibility to a different tool.

- **Auth:** Clerk is the source of truth (`@clerk/expo` custom flows on our own screens, session in `tokenCache` via `expo-secure-store`). Use the method-based API (`signUp.password`, `verifications.verifyEmailCode`, `finalize`), never `@clerk/expo/legacy`. Google and Apple use `useSSO` (browser flow, works in Expo Go). Clerk errors are shown through `authMessage` in `src/lib/auth.ts`. The app is "Roam" in the user's own workspace, linked with the Clerk CLI; the Clerk MCP is signed into a different workspace and can't see it, so change instance config with `npx clerk@latest config patch` (dry run first). Password `min_length` 8 matches `validate.ts`; change both together. Account edits use `user.update`, `user.updateMetadata` (home city in `unsafeMetadata.homeCity`, read with `homeCity()` in `src/lib/account.ts`; saved stays in `unsafeMetadata.saved` as `{ [stayId]: savedAtISO }`, a map so deep merge keeps devices from clobbering each other, capped at 150 for Clerk's 8 KB metadata limit; move to a database when bookings arrive) and `setProfileImage` (base64 from `expo-image-picker`). `session.revoke()` and `user.delete()` go through `useReverification` with `useReverifySheet` (`src/components/account/reverify-sheet.tsx`, email-code `CodeInput` shared with `verify`); a closed sheet throws `reverification_cancelled` (`isReverificationCancelled`). Delete self is on in Clerk and gates the Delete row via `user.deleteSelfEnabled`. PostHog persons carry only the Clerk user ID (persons identified before plan 17 still hold email and name). Host companies are Clerk Organizations: membership optional (`force_organization_selection: false`, guests never see a company step), 20 members max, Hobby plan roles `org:admin` and `org:member` only, both holding the custom permission `org:stays:edit` (custom roles need Clerk's paid B2B add-on). Roam creates each company and invites its first admin with `npx clerk@latest api` (`POST /v1/organizations`, then `/invitations`), then sets `host.clerkOrgId` in Studio; there's no create-company UI. Org screens are ours on `useOrganization`/`useOrganizationList` (Clerk's org components are web only). Clerk's `org:sys_*` permissions aren't in session claims, so the team UI reads `membership.permissions` and API routes check `org:stays:edit`. These settings and the permission exist on the development instance only so far.
- **Content:** Sanity project `crc5fllu`, dataset `production`. Studio is a standalone app in `studio/`, and the schema lives in `studio/schemaTypes/`, deployed with the CLI from there (the MCP's `deploy_schema` refuses projects with a local Studio). The Sanity MCP verifies the deployed schema, runs content queries and changes, and manages embeddings. `studio/seed/seed.ts` upserts by `_type` + slug from `studio/seed/data.ts` with `patch().set()` (never `createOrReplace`, never deletes, never writes a stay's `description`); photos are Unsplash images uploaded as assets (deduped by hash).
- **Stay copy:** `description` is written only by `studio/copy/write-copy.ts`: Agent Actions Generate (`noWrite`, in-memory `create`, so old text is never context) from the typed fields in `FACTS_PROJECTION` alone, never price or rating. It's kept only when both checks find nothing invented: the code check `findUnsupported` (`copy/grounding.ts`: numbers, feature words, mid-sentence names) and an Agent Actions Prompt judge (JSON, temperature 0). It gets 3 attempts, each fed the flagged claims. Pass patches the published stay; failure leaves the copy in `drafts.<id>` for review in Studio. A run keeps any description that already passes, and logs a stay whose request errors before moving on, so re-running resumes. Run it after seeding new stays, and after host edits (they don't regenerate copy). Copy from typed fields alone is plain (it restates fields and rules); richer copy needs more facts on the stay, which is a schema decision.
- **Content model:** `property` holds every guest filter as a typed field (`nightlyPrice` whole USD, `maxGuests`, `bedrooms`, `bathrooms`, `propertyType`, `setting`, `amenities` camelCase values, `petsAllowed`, `location.city/region/country`), plus `photos` (first is the cover, `alt` required), plain-text `description`, `tags`, `houseRules`, and check-in/out `HH:MM`. It references a `host` (name, photo, bio, and optional unique `clerkOrgId`: the Clerk organization whose members edit the host's stays, so a stay belongs to a company through `property.host`) and one `policy` with `kind == "cancellation"`. Other policy kinds (booking, payment, pets, damage, checkIn, conduct) apply to every stay and aren't referenced. Free cancellation is `freeCancellationHours > 0`: fetch those policy IDs first, then filter `cancellationPolicy._ref in $ids`. Home chips map Cabins/Villas to `propertyType` and Beach/City to `setting`. Long text is plain text with blank-line paragraphs, never Portable Text.
- **App reads:** `src/lib/sanity.ts` (`sanityFetch`, `imageUrl`) queries the public dataset over the `apicdn` with plain `fetch`, no token and no client library; values go in params. CDN reads can lag edits by about a minute. Home loads all stays once through `useStays()` (`src/lib/stays.ts`, highest rated first, card fields only), and its chips filter that list locally. `useStay(id)` fetches one stay with its host, cancellation policy, and the all-stay policies in one query (`null` = not found). Host screens read `useHostStays(orgId)` with `sanityFetch(…, cdn = false)` (the live API, still public and tokenless) so a host sees their own save at once.
- **Search:** `src/lib/search.ts` (pure, checked by `npx tsx src/lib/search.check.ts`) parses the sentence into exact filters and builds the GROQ; leftover words are the soft intent. `place` matches the stays' own cities, regions, and countries plus US state names (codes only in capitals). `useSearchMeta`/`useStaySearch` (`src/lib/stays.ts`) run it over the public CDN with a once-per-session meta query (places plus free-cancellation policy IDs). A search runs on submit, chip, sheet, or sort, never per keystroke (semantic queries use quota). A sentence of only soft words never comes back empty. Data files import no UI (badges, `AMENITY_BADGES` and `SETTING_BADGES`, live in `src/components/stays/amenity-icons.ts`) so the check runs under Node.
- **Exact constraints** (price, guests, bedrooms, bathrooms, type, setting, amenities, pets, place, free cancellation): GROQ filters, with values always passed as params.
- **Soft intent** (quiet, cozy, secluded): Dataset Embeddings via `text::semanticSimilarity()` inside `score()`, plus `boost(tags match $softWords, 1)` (a `count(...) > 0` boost is rejected inside `score()`). The embeddings projection covers `property` only (title, description, tags, propertyType, setting, amenities, houseRules, city, region); change it with `datasets embeddings enable production --projection=…` through the MCP CLI.
- **Policy knowledge:** until Jev and Context are wired up, `src/lib/ask.ts` picks topics with a keyword map (checked by `npx tsx src/lib/ask.check.ts`) and builds cards from `useStay` (its `policies` carry `kind`). The target is a Sanity Context endpoint in Knowledge Base mode. Context endpoints are created in the Dashboard's Context app and read with an organization token (Context Viewer), per https://www.sanity.io/docs/ai/context-migration-guide. One endpoint serves one mode. The Context skill still describes `sanity.agentContext` Studio documents with a project token; that route is deprecated, so don't use it.
- **Typed decisions** (which stay topics and policies answer a question): Jev, called from API routes through the AI SDK's `experimental_evaluate` with the `@ai-sdk/typesafe-ai` provider and `TYPESAFE_AI_API_KEY`. No Vercel AI Gateway. Keep `ai` and `@ai-sdk/typesafe-ai` pinned to exact versions, since the API is experimental.
- **Answer text:** none generated. Answers show the stay's own fields and policy text word for word, with their source. No LLM runs in the app.
- **Styling:** NativeWind v5 RC (Tailwind 4) via `className`. Setup follows https://www.nativewind.dev/v5/llms-full.txt: `src/global.css` (imported once in `src/app/_layout.tsx`), `metro.config.js`, `postcss.config.mjs`. Keep `nativewind`, `react-native-css`, `tailwindcss`, `@tailwindcss/postcss`, and `lightningcss` pinned to exact versions, with the `lightningcss` override in `package.json`.
- **Design system:** tokens live only in `@theme` in `src/global.css` (Tailwind's default colors, radii, fonts, and text sizes are wiped; `--spacing` is 4px because NativeWind's native rem is 14). Shared components live in `src/components/ui/`, and `/design-system` previews them all. Screens use `Text` and `Icon` from there, never raw `fontSize`, `fontFamily`, or hex values. The font is Plus Jakarta Sans, with weight picked by family (`font-regular|medium|semibold|bold|extrabold`; display and title use ExtraBold with negative tracking) and loaded with `useFonts` in the root layout. Icons are `lucide-react-native` (pinned exact) through `Icon`. Brand marks are `GoogleLogo` and `AppleLogo` (`brand-logo.tsx`, `assets/images/*.svg` through `expo-image`, no SVG transformer). `Input` takes `label` for the two-line auth field, `IconButton` has `outline` and `size="sm"`, `Text` has `underline` for links and a `hero` variant (46, Home title only), `Wordmark` has `size="hero"` (38), `Chip` has `size="soft"` (grey idle, compact, three per row), `ListRow variant="policy"` has a headline title and caption subtitle, `Badge size="sm"` is the listing card's pill and the only user of the `tiny` text token (11), `ListGroup` is the titled canvas section with inset dividers for `ListRow variant="menu"` (canvas icon tile), `ListRow` also takes `iconTile={false}` (policy), `tone="danger"`, and `trailing`, `ListingCard` has a flush image and the save heart as a canvas circle on the card, and `Button` takes `leading` for a non-lucide leading element. Never pass an inline `style` to a `TextInput` that has a `className`: react-native-css then drops the whole class (font, size, flex). The app icon (1024 PNG, no alpha), Android adaptive layers and splash mark are the wordmark in ink on `--color-primary`, rendered from `roam-wordmark.svg`. The logo is `Wordmark` (path generated from Plus Jakarta Sans Bold; source `assets/images/roam-wordmark.svg`), never `Text`. The app is light only (`userInterfaceStyle: light`). Text-size line heights are unitless ratios, never px (native multiplies the bare number by the font size). There is no class merging, so components split `variant` (size and family), `tone` (color), and `className` (layout only), and never emit two classes for the same property. JS props that need a token color (icon color, Switch track) get it through a `styled(…, { nativeStyleMapping: { color: true } })` base, never hex or `useUnstableNativeVariable` (throws on web). The native tab bar gets its tint the same way (`styled(NativeTabs, …{ color: "tintColor", backgroundColor: "indicatorColor" })`).
- **Motion:** Reanimated, following the expo-animation skill. Press feedback is `PressableScale` (scale 0.97, 120 ms CSS transition), used by `Chip`, Home's buttons and cards; `ListingCard` scales card and heart together with the exported `pressScale(pressed)`. Cards in scroll views set `unstable_pressDelay={80}` so a scroll doesn't flash them. Chip selection color eases with `transition-colors duration-200 ease-out`. Other components keep `active:opacity-70`. Lists that refilter wrap rows in `Reflow` (fade + `LinearTransition`, 200 ms, skipped under Reduce Motion). Tab switches never animate.
- **Payments:** Stripe PaymentSheet on a PaymentIntent (`@stripe/stripe-react-native` and server `stripe`, both pinned exact; `StripeProvider` in the root layout). `POST /api/bookings` re-reads the price from Sanity (`api.sanity.io`, never the app's number), creates the PaymentIntent (no `payment_method_types`, no Customer), then holds the nights. Only the webhook `src/app/api/stripe/webhook+api.ts` (`payment_intent.succeeded`) confirms a booking, never the app. Server key is a restricted `rk_` key; development uses the "RN Roam" Stripe sandbox, and `stripe listen --forward-to localhost:8081/api/stripe/webhook` writes nothing (its `whsec_` goes in `.env.local`). The hosted routes have no Stripe webhook registered yet (skipped for the portfolio demo), so bookings made against `rn-roam.expo.app` stay pending, the app shows "Payment received", and they never reach Trips.
- **Bookings:** private Sanity dataset `bookings` (never `production`), read and written only by API routes through `src/lib/server/bookings-store.ts` (plain fetch, `SANITY_BOOKINGS_TOKEN`). A `booking` (generated ID, `stayId` string, `guestId` Clerk ID, dates, `totalCents`, `status` pending/confirmed/expired, `paymentIntentId`, `expiresAt` 15 min) is created in one mutate with one `night` lock per night, ID `night.<stayId>.<YYYY-MM-DD>`, so overlapping holds fail atomically. A blocking hold is released only if it's unpaid and expired or the same guest's, and only after its PaymentIntent is cancelled. Dates, nights (1 to 28) and price live in pure `src/lib/booking.ts` (`npx tsx src/lib/booking.check.ts`); "today" is UTC on the server.
- **Host edits:** `PATCH /api/host/stays/[id]` (`authOrg` in `src/lib/server/auth.ts`: 401 signed out, 403 without an active company or `org:stays:edit`) validates with pure `validateStayPatch` (`src/lib/host.ts`, `npx tsx src/lib/host.check.ts`: `nightlyPrice`, `maxGuests`, `petsAllowed`, `amenities`, check-in/out, `houseRules` only), then `src/lib/server/stays-store.ts` (`SANITY_API_WRITE_TOKEN`) checks `host->clerkOrgId == orgId` (404 for missing and other companies' stays alike) and patches the published stay with `ifRevisionID` (409 on a race). Edits go live with no review. A Studio draft of the same stay overwrites them when published.
- **Hosting:** API routes need `web.output: "server"`; they run on EAS Hosting at `https://rn-roam.expo.app` (Cloudflare Workers: fetch-only, no TCP), which is also the `expo-router` plugin `origin`. Deploy with `npx expo export --platform web` then `npx eas-cli@latest deploy --prod --environment production`; the production alias can serve the previous deploy for a minute or two. The web export renders every screen, so `metro.config.js` swaps native-only packages (`@stripe/stripe-react-native`, `@expo/ui`) for `src/lib/native-only-web-stub.js` on web (add any new native-only package there), and maps `stripe` to its worker build. Server code creates clients and reads `process.env` per call, never at import. EAS project `@shangnik/roam`, bundle ID and Android package `com.yeldynov.roam`. `eas.json` profiles: development, preview (Android APK, internal), simulator (iOS Simulator app for Appetize), production (store, remote auto-incremented version); preview and simulator use the `production` environment. That environment holds the six server secrets as "sensitive" (EAS Hosting can't deploy "secret") and the four `EXPO_PUBLIC_` values as plain text (`.env.local` never reaches EAS). `src/lib/server/*` holds secrets and is imported only by `src/app/api/**`. The app calls routes with relative URLs through `apiFetch` (`src/lib/booking-api.ts`), which adds the Clerk token.
- **Analytics:** PostHog, identified by Clerk user ID only (never email or name). Dev and production share one project; `before_send` in `src/lib/posthog.ts` adds `environment` (`development`/`production`) to every event, since `reset()` clears super properties. Each completed search sends `stay_search_results_shown` or `stay_search_no_results` with `results_count`, `query_length`, `trigger`, `sort`, `filter_kinds`, enum values (`property_types`, `settings`, `amenities`), `pets`, `free_cancellation`, `has_soft_intent`; never the text, place, prices, or soft words. The unfiltered landing list sends nothing. Account sends `profile_updated` (`fields`: name/city/photo), `session_revoked`, `account_deletion_started`, `account_deletion_cancelled` (`step`: confirm/reverify), and `account_deleted` (flushed before the guard resets PostHog), never the values. Opening a stay sends `stay_viewed` once it loads, with `stay_id`, `source` (`home`, `search`, `saved`, `trips`, `link`), `property_type`, `setting`. `stay_saved`/`stay_unsaved` send `stay_id` and `source` (`search`, `stay`, `trips`) after the Clerk write succeeds; never the saved list or count. Booking sends `booking_started` (`stay_id`), then `booking_quote_failed` (`reason`), `booking_payment_opened`, `booking_payment_cancelled`, `booking_payment_failed` (Stripe `code`), `booking_completed`, each with `stay_id`, `nights`, `guests`; never dates, amounts, or payment IDs. Hosting sends `host_mode_entered` (each time Hosting opens on a company: `org_id`, `org_role`), `host_stay_updated` (after a 200: `stay_id`, `fields_changed` key names, `org_id`, `org_role`), `host_stay_update_failed` (`status`, 0 = no answer, `org_id`), `host_member_invited` (`role`), and `host_invitation_accepted` (`org_id`); never emails, names, prices, or rule text.

## Rules

- Secret keys (Clerk secret key, Clerk JWT key, TypeSafe key, Sanity organization token, Sanity write and bookings tokens, Stripe secret key, Stripe webhook secret) never reach the app bundle. Use them only in API routes and local scripts such as seeding. Never put them behind `EXPO_PUBLIC_`, which is bundled into the app. Never commit `.env`. Keep variable names, without values, in `.env.example`.
- Sanity Context needs a deployed Studio for the dataset. Redeploy Studio from `studio/` after schema changes.
- Jev is not an agent. It answers typed questions (Choice, Noul, Score) with probabilities. It never writes GROQ, calls tools, or generates text. Code builds queries from its answers.
- Prices, guest counts, and dates are parsed in code. Jev may choose between candidates code found, but never produces the value.
- Embeddings rank, they don't filter, and they only see the document itself (no references). Hard constraints are always GROQ filters, and text that should affect ranking lives on the property document.
- Policy answers show only text from the stay's data and Roam's policies, word for word. If nothing answers the question, say so and point to support.
- API routes verify the Clerk session before doing any work (`authUserId`, or `authOrg` for host routes, in `src/lib/server/auth.ts`). The Stripe webhook verifies Stripe's signature instead.
- PostHog failures never block the app. Never send what guests type, tokens, or personal data in events.
- Let Sanity generate document IDs (the one exception: booking `night` locks). Model relationships as references.
- Ask before adding a dependency or service, changing the Sanity schema once content exists, or deleting data. Prefer Expo modules over third-party libraries.
- Whenever you need input from the user, ask through your tool's built-in question panel so they pick from options instead of typing. Give two to four clear options with the recommended one first. Fall back to plain text only if no such panel exists.

## How we build features

For a new feature or a change across several files. Small fixes and questions skip this.

1. **Understand.** Read the code involved. Open an earlier plan only if this feature builds directly on it (pick by file name). Read the current docs pages for the APIs you'll use, and load a matching skill if one exists (e.g. the Expo, Clerk, Sanity, Sanity Context, or TypeSafe skills). Don't write version-specific APIs from memory.
2. **Ask.** If a real decision is unclear (scope, visible behavior, data shape), ask in the question panel, batching questions into one round and following up only if the answers raise new ones. Pick defaults for the rest and list them. If a decision in this file looks wrong, raise it instead of changing it.
3. **Plan.** Copy `prompts/TEMPLATE.md` to `prompts/NN-feature-name.md` (next number) and fill it in. The plan must be self-contained, so a fresh session can build it from this file plus the plan alone.
4. **IMPORTANT: stop and wait.** Write no app code until the user approves the plan. Ask for approval in the question panel (approve, or request changes). If they request changes, update the plan and ask again. On approval, set `Status: approved`.
5. **Build** step by step, checking each one. If a step turns out wrong, stop and explain instead of redesigning.
6. **Close out.**
   - Run the plan's Verification and give the report described under Reporting.
   - Add a short `## Result` to the plan and set `Status: done`.
   - Update this file: put each lasting decision in the section it belongs to. Replace or remove rules that are no longer true instead of appending. Keep this file under 150 lines.

## Building from designs

Designs are attached in the chat. Screens must match them exactly: layout, spacing, sizes, colors, type, radii, icons, and copy.

- Icons, fonts, and brand images come from `assets/` or the chosen icon library, never recreated from a screenshot. Sample property photos may be remote placeholder images. If an asset is missing, use a marked placeholder and list it.
- Map every color, font, spacing value, and radius to a design-system token. List values with no token in the plan as proposed new tokens instead of hardcoding them. When creating the design system itself, derive the tokens from the designs.
- UI plans describe the design (elements, states, tokens, assets) well enough to build without the image. If building in a new session, ask for the design to be attached again.
- After building, check the screen on the user's iPhone through macOS iPhone Mirroring, then compare it with the design. List every difference, fix, and repeat. Report which values were estimated from an image.
  - The user runs `npx expo start` and opens the screen on the phone. You can see the phone but can't tap or type on it, so ask the user to navigate when needed.
  - Before every capture, ask the user (in the question panel) to reload the app (press `r` in the Expo terminal) and open the screen, so the screenshot shows the latest code.
  - Capture with `screencapture -x <scratchpad>/screen.png` (a normal sandboxed Bash call; VS Code has Screen Recording permission), then Read the image. It captures the whole display, so find the iPhone Mirroring window in it.
  - A restyled screen proves the change only when nothing else could produce that look. For example, a `className` layout with no `StyleSheet` fallback.
  - This Mac has no Xcode CLI, so `xcrun simctl` isn't available. If Xcode is installed later, the iOS simulator works too: `xcrun simctl openurl booted <url>` (scheme in `app.json`) and `xcrun simctl io booted screenshot <path>`.

- **Verified:** each check with ✅ or ❌ and its evidence (command output, screenshot). List what wasn't checked as ❌ with the reason. Never mark something ✅ without running it.
- **You need to:** numbered actions only the user can take, such as keys, dashboard settings, manual steps in Sanity, or assets to provide.
- **Test it yourself:** numbered steps to reproduce the result from a fresh start, ending with `Expected:` and what the user should see.
- **Notes:** defaults picked, trade-offs, and anything left for later.
